# Требования к системе прогноза пассажиропотока

Неделя 1 · ведёт Мамаев Никита (Product Owner)

## 1. Цель

Дать диспетчерской службе и планировщикам расписания почасовой прогноз входов пассажиров
по станциям одной линии метро на 7 дней вперёд и возможность оценить влияние событий
(закрытие станции, мероприятие, погода, изменение интервала движения).

## 2. Границы проекта

| Входит | Не входит |
|---|---|
| Пилотная линия: Сокольническая, 26 станций (Бульвар Рокоссовского — Новомосковская) | Другие линии, пересадочные потоки между линиями |
| Входы через турникеты по часам 5:00–23:59 | Выходы, ночные часы, наполняемость поездов |
| Горизонт 7 дней, пересчёт раз в сутки | Оперативный прогноз внутри дня |
| Сценарии «что-если» поверх прогноза | Автоматическое построение расписания |

## 3. Протокол интервью с заказчиком

Вопросы подготовлены до встречи. Ответы взяты из задания на проект. Пункты с пометкой
**уточнить** заказчик пока не подтвердил: они вынесены в раздел 7.

| № | Вопрос | Ответ |
|---|---|---|
| 1 | Кто будет пользоваться прогнозом? | Диспетчер линии и планировщик расписания |
| 2 | На сколько дней вперёд нужен прогноз? | 7 дней |
| 3 | С какой детализацией? | По станциям и по часам, с фильтрами по дате, станции, участку линии и времени |
| 4 | Как часто обновлять? | Раз в сутки (ночью, после поступления фактов за прошедший день) |
| 5 | Какая точность нужна? | Не ниже 85% (точность = 100% − MAPE) |
| 6 | Какие сценарии важны? | Закрытие станции, массовое мероприятие, погода, изменение интервала |
| 7 | Какие данные есть у заказчика? | Почасовых данных нет; открытые данные + синтетика с той же схемой — **уточнить** доступ к АСКП |
| 8 | Где должна работать система? | Веб-интерфейс + REST API, контейнеры — **уточнить** инфраструктуру заказчика |
| 9 | Как проверяем точность? | На последнем полном годе, который модель не видела при обучении |

## 4. Функциональные требования

| ID | Требование | Приоритет | Где реализуется |
|---|---|---|---|
| FR-1 | Почасовой прогноз входов по каждой станции линии на 7 дней | Must | `POST /forecast/run`, `GET /forecast` |
| FR-2 | Фильтры: даты, станции, участок линии (от–до), часы | Must | параметры `/forecast`, `/history` |
| FR-3 | Агрегация: по часам, по дням, по станции, по линии за день | Must | параметр `agg` |
| FR-4 | Ежедневный автоматический пересчёт прогноза | Must | планировщик / CronJob |
| FR-5 | Просмотр фактических данных за прошлые периоды | Must | `GET /history` |
| FR-6 | Сценарий «закрытие станции» с перераспределением на соседние | Must | `POST /whatif` |
| FR-7 | Сценарий «мероприятие у станции» | Should | `POST /whatif` |
| FR-8 | Сценарий «погода» (температура, осадки) | Should | `POST /whatif` |
| FR-9 | Сценарий «изменение интервала движения» | Could | `POST /whatif` |
| FR-10 | Дашборд: карта линии, графики прогноза, форма «что-если» | Must | Streamlit (нед. 7) |
| FR-11 | Просмотр метрик качества текущей модели | Should | `GET /model/metrics` |

## 5. Нефункциональные требования

| ID | Требование | Как проверяем |
|---|---|---|
| NFR-1 | Точность ≥ 85% на тестовом году (MAPE ≤ 15%) | `metrics.json` после обучения |
| NFR-2 | Пересчёт прогноза на 7 дней — не дольше 5 минут | лог `forecast run`, метрика Prometheus |
| NFR-3 | Ответ API на запрос прогноза — до 1 секунды | метрики `/metrics` |
| NFR-4 | Сбой загрузки данных не портит данные в БД | ETL в одной транзакции, тест |
| NFR-5 | Данные проходят проверки качества до загрузки | `metro.validate`, стадия DVC |
| NFR-6 | Воспроизводимость данных и экспериментов | DVC, MLflow |
| NFR-7 | Развёртывание одной командой | `docker compose up` |
| NFR-8 | Мониторинг работы сервиса и свежести прогноза | Prometheus, Grafana |

## 6. Ограничения и допущения

- Почасовых открытых данных по входам нет. На data.mos.ru публикуются только квартальные входы
  по станциям, поэтому почасовые ряды синтетические. Объём каждой станции калибруется
  по реальным квартальным данным. Долю синтетики указываем в отчёте.
- Погода на дни прогноза — климатическая норма. Реальный прогноз погоды подключим, если
  появится источник.
- Праздники и переносы берём из производственного календаря РФ.
- Коэффициенты правил «что-если» (доля перераспределения 60%, эластичность по интервалу 0,15) —
  допущения проекта. Их надо уточнить у заказчика.

   до «Новомосковской».

4. Какие события заказчик знает заранее (календарь мероприятий «Лужников» и др.)?
5. Где будет развёрнута система и как к ней подключаются пользователи?
